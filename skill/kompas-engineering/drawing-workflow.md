# Оформление видов и компоновка в КОМПАС

Инженерные решения (состав изображений, размерная схема, базы, точность) — по `drawing-preparation`.
Здесь — работа хелперами после согласования этих решений. Все создания, изменения метаданных и переносы —
в `change_begin` → `code_exec` → `change_end`; чтение — `query`. Точные сигнатуры берите через `api_doc('kh.…')`.

Известное ограничение v19: `drawing_layout_evaluate` и `drawing_layout_optimize`
создают временную копию через нативное сохранение, которое сбрасывает историю Undo
исходного документа. Само размещение и сохранение привязок проверены, но отмена
такого этапа пока не гарантируется. До исправления выполняйте эти инструменты
на отдельной сохранённой рабочей копии, сохраняя исходный документ отдельно.

## 1. Создать виды и оформить каждый

На новом чистом чертеже постройте нужные `kh.view_assoc`, `kh.section_view`, `kh.remote_element` во временных
разнесённых позициях. Рабочий масштаб задайте сразу. Не тратьте проходы на окончательную раскладку пустых видов.
Существующий чертёж человека не очищайте ради этого порядка.

Направление проекции удобно выбрать до построения: в `query` по открытому документу модели вызовите
`kh.projection_catalog(doc=doc, points={'база': [x,y,z], 'ориентир': [x,y,z]})`. Каталог читает именованные
ориентации модели и возвращает оси `right/up`, их знаки и координаты контрольных точек. Например, условие
«ориентир выше базы» проверяется по второй координате, без создания пробных видов. Выбирайте запись с
`selectable_by_name=True`; `depth` — локальная Z проекции, а не проверка видимости поверхностей.
Если нужное изображение согласовано, сначала сопоставьте его с каталогом; повторный перебор видов обычно
не нужен. Видимость отверстий и полноту разреза всё равно проверяйте по готовому изображению.

В `view_assoc`, `section_view` и `remote_element` можно сразу передать `angle=` (поворот на листе),
`settings=` (состав и отображение) и `points=` (контрольные точки модели). Направление проекции и поворот
на листе — разные параметры. Пример частичных настроек:

```python
settings = {'hidden_lines': {'compute': True, 'show': True},
            'auto': {'axes': False, 'centres': False},
            'caption': {'name': False, 'scale': False}}
r = kh.view_assoc(src, projection_name, 1.0, at=(150, 180),
                  angle=90, settings=settings, points={'база': [0, 0, 0]})
result = r['summary']
```

Незаданные настройки сохраняют нативное поведение: не отключайте все `Project*` наугад.
`summary` показывает фактические настройки, оси в координатах вида и листа, проекции контрольных точек,
габарит контура и количества объектов. `unavailable` явно перечисляет то, что не удалось измерить.
Габарит контура здесь не заменяет полный габарит оформленного вида `view_bounds`.
`kh.view_settings(v)` читает состояние; тот же хелпер с `settings=` или `angle=` меняет существующий вид
в этапе, перестраивает нужную геометрию и проверяет настройки чтением. Полную схему берите через
`api_doc('kh.view_settings')`. Для локальных точек после поворота используйте `to_sheet`/`to_view`;
`model_to_view` возвращает координаты до масштаба и поворота листа.

На каждом виде создайте предусмотренные `kh.dim*`, `kh.leader`, `kh.rough`, `kh.datum`, `kh.tolerance`, `kh.text`.
Передавайте `layout=` при создании: краткий словарь настроек или полную версионную политику из
`kompas_agent.annotation_layout.policy(kind, ...)`. `group` и `order` задавайте по смыслу размерной схемы, `priority` — по
важности чтения; не назначайте группы по близости или одинаковому номиналу. `moves` ограничивает возможности
перемещения, `locked` фиксирует обозначение. Источник конфигурации задаёт `layout_source=`.
Общие параметры группы хранит `annotation_layout.set_groups(..., source=...)`.
Группа без явного типа означает координатное выравнивание: объединяйте так только совместимые параллельные
размеры одного вида. Для смыслового набора разнородных обозначений задайте группе `type='annotation_set'`
или `type='reading_group'`; название элемента детали само по себе не задаёт общую размерную линию.
Если выравнивание не нужно, `group` можно не задавать. Не придумывайте ограничения ради заполнения метаданных.
Для полной политики или групп импортируйте `from kompas_agent import annotation_layout`; справка —
`api_doc('annotation_layout.policy')` и `api_doc('annotation_layout.set_groups')`.

Сохраните адреса созданного в записной книжке. Геометрические привязки берите из самого вида; после создания
проверяйте фактический номинал и `bound`, а не только отсутствие исключения. Опорную поверхность шероховатости
задавайте явно, если ближайший отрезок неоднозначен. Базы и рамки допусков создавайте объектами КОМПАС,
а не заменяйте текстом в ТТ только из-за отсутствия знакомого примера.

Например, в одном `code_exec` создание возвращает адрес `obj`, пригодный для дальнейшей правки:

```python
d = kh.dim(1, (0, 0), (40, 0), 30, 'h',
           layout={'group': 'ширины', 'order': 0}, layout_source='agent: согласованная размерная схема')
result = {'obj': d['obj'], 'nominal': d['nominal'], 'bound': d['bound']}
```

`kh.line_intersection(l1, l2)` вычисляет пересечение бесконечных 2D-прямых. Это только координаты,
не ассоциативная опорная геометрия: размер до вычисленной точки без нативных связей остаётся свободным.

## 2. Расставить обозначения и исправить проблемы

Сначала создайте на листе все нужные размеры и обозначения по размерной схеме; начальные позиции могут быть приблизительными.
Затем запустите оптимизацию для каждого оформленного вида и проверьте отчёт и изображение.
После оптимизации вручную поправьте оставшиеся конфликты. Не подменяйте этот проход серией ручных сдвигов.
Если оптимизация завершилась ошибкой, разберитесь в причине и повторите; если она неприменима, укажите конкретное ограничение и закончите расстановку вручную.

Для одного ещё не скомпонованного вида вызывайте отдельный MCP-инструмент
`drawing_layout_optimize(view_ids=[номер], space='view')` в открытом этапе. Этот режим не ограничивает
оформление случайными соседями, рамкой или штампом временного листа. Перед запуском для диагностики можно
вызвать `drawing_layout_evaluate` с теми же параметрами; повторное вычисление до каждого запуска не требуется.
В этом режиме указывайте ровно один несистемный вид; смысловые группы расстановки не объединяйте между
видами. Общие сведения об одном элементе детали могут быть на разных изображениях, но это не общая группа
координатного выравнивания.

Стратегия `snapshot-layout` снимает геометрию и управляющие параметры один раз. Все кандидаты,
групповые ярусы размеров, вееры от якорей, жадный проход, annealing и обмен полок рассчитываются
в памяти. Затем адаптер применяет выбранные команды одним пакетом и повторно измеряет результат.
Новые внешние ярусы учитывают полный контур вида; существующие смысловые группы имеют приоритет
перед автоматически выведенной вложенностью интервалов. Видимость исходных объектов не меняется.

В `optimizer.diagnostics` находятся ход поиска, зоны, скопления якорей и нерешённые конфликты.
`integrity.prediction` отдельно показывает, где прогноз габаритов разошёлся с CAD: это не доказательство
повреждения содержимого и не основание принимать расстановку без картинки. Номиналы, текст,
нативные связи и управляющие параметры проверяются отдельно. `unsupported_pool` перечисляет
сохранённые неподдержанные положения. Автоматическое представление нелинейного размера не
переводится на ручную полку; существующие ручные полки поддерживаются. Скольжение допускается
только для выносок с подтверждённой точной исходной кривой, видимым диапазоном и неизменной связью.
Для символов и аппроксимированных кривых контакт сохраняется.
Прочитайте отчёт `before`/`after`, участников конфликтов и целостность, затем посмотрите `view_capture`
нужного вида. Геометрические пересечения — факты для проверки, не автоматическое доказательство нечитаемости.
`not_sampled`, неизвестные связи и неподдержанные объекты не превращайте в `pass`.
В `document_untouched` поле `ok` подтверждает проверку сохранности содержимого и восстановление окна
с точностью нативного растра. `side_effects` отдельно сообщает, если чтение КОМПАС пометило документ
изменённым; это не означает изменение чертежа. Ради сброса этого флага сохранять документ не требуется.

Для исправления уже созданного используйте:

- `kh.annotation_get` / `kh.annotation_list` — фактические значения, параметры, метаданные и адреса;
- `kh.annotation_update` — содержание и метаданные расстановки;
- `kh.annotation_place` — локальное положение текста, полки или размерной линии;
- `kh.annotation_delete` — удалить конкретное обозначение, когда сведения нужно создать на другом виде;
- `kh.tech_req_get/update/place` — отдельно содержание и положение ТТ.

`annotation_update(obj, layout={'priority': 80})` меняет часть политики, не требует передавать её целиком.
Для размера `tol=''` снимает посадку, `dev=None` снимает отклонения, `reference=True` делает справочным;
`annotation_place(obj, at=[x, y])` задаёт положение в мм вида, `radius=` — дугу углового размера,
`angle=` — направление диаметрального/радиального, `text_at=` — отдельное положение текста линейного,
углового или радиального размера на нативной полке. Для диаметрального используйте `text_shift=`:
целочисленная нативная длина ножки в мм листа, независимо от масштаба (0 и ±1 — специальные положения,
сверяйте по справке). Для надписи вида
`kh.view_label(v, at)` принимает мм листа.
`annotation_update(..., tips=[...])` меняет ветви выноски/позиции/допуска, `anchor=...` — опорный объект
шероховатости в том же виде, `angle_kind=` — вариант углового размера. После смены варианта сверяйте номинал.
Поддерживаемые поля конкретного типа проверяйте по справке, неизвестные не передавайте наугад.

Сведения на другое изображение переносите удалением исходного обозначения и созданием нового по геометрии
целевого вида, с переносом нужного содержания и метаданных. Сверьте измеряемую величину и привязки нового
объекта. Универсального переноса по координатам между видами нет.

После изменения содержания, метаданных или состава обозначений повторно оптимизируйте затронутый вид.
Если остались одиночные конфликты — поправьте `annotation_place` и проверьте результат. Не запускайте
одинаковую оптимизацию бесконечно без изменения входных условий.

## 3. Самостоятельно скомпоновать готовые виды

Через `kh.view_bounds(v)` получите полный габарит каждого оформленного вида: геометрия, размеры, надписи,
линии и обозначения. Контур `sheet_box` без оформления для этого недостаточен. Используйте возвращённые
координаты `full.sheet` и `full.view`; `complete=False`/`unmeasured` означают неполный замер — сначала
выясните, какие объекты не учтены. Для повёрнутых видов прямоугольники консервативные; единицы и учёт
поворота сверяйте по контракту хелпера.

Рассчитайте позиции блоков кодом с учётом проекционных связей, рамки, ТТ, штампа и промежутков. Координаты
выбирает агент, автоматический компоновщик не требуется. Примените `kh.place_view(v, at, vpt)` для каждого
вида: переносите целый вид, не двигайте по отдельности принадлежащие ему размеры. Масштаб при этом сохраняйте.
Если его пришлось изменить, заново проверьте читаемость и расстановку затронутого вида.

После компоновки вызовите `drawing_layout_evaluate(space='sheet')` без ограничения одним видом: этот режим
учитывает соседей, рамку и штамп. Исправьте оставшиеся конфликты листа и выполните `validate` плюс отдельный
нормоконтроль по доступному `drawing-review`; без него — отдельную самопроверку из
`drawing-preparation`. Проверка вместимости не заменяет оценку расстановки обозначений.
Закройте этап и сохраняйте отдельным инструментом по разрешённому объёму задачи.
